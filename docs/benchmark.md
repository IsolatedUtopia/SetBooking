# 并发抢座压测记录

## 1. 目标

验证一个具体问题：**同一座位的同一时段被多个请求同时预约时，系统是否会出现超卖（一个格子被多人占用）。**

要证明的命题：

1. 防超卖的正确性来自数据库的唯一约束，而不是应用层的"先查再插"。
2. 应用层的检查（封禁、日期窗口、每日上限、用户自身重叠）在并发下**全部无法阻止**同一格子被重复写入。
3. 数据库拒绝后，接口层把 `IntegrityError` 翻译成 `409`，用户看到的是明确的业务冲突，而不是 500。

## 2. 环境

| 项 | 值 |
| --- | --- |
| 系统 | Windows（本机，127.0.0.1） |
| Python | 3.14.10 |
| Web | FastAPI + uvicorn（单进程，未开 `--reload`） |
| ORM / 驱动 | SQLAlchemy 2.1.8 (async) + aiomysql 0.3.2 |
| 数据库 | MySQL 8.0.46 |
| 并发客户端 | httpx.AsyncClient + `asyncio.gather`，20 个用户 |

按"座位 × 日期 × 30 分钟"离散成格子：08:00–22:00 共 28 格。一次预约 1–4 个连续格子，落库时展开成 `reservation_slots` 明细行，每行是一个被占用的格子。

## 3. 防超卖的机制

`reservation_slots` 上的唯一约束：

```sql
UNIQUE KEY uq_reservation_slots_seat_slot (seat_id, date, slot_index)
```

一个座位在某天某格只允许存在一行记录。两个事务同时插入同一格子时，后提交者会收到 `IntegrityError`，服务层捕获后返回 409。

## 4. 实验 A：唯一索引生效

**操作**：20 个已登录用户同时预约同一座位、同一天、时段 0–2（2 个格子）。

**预期**：1 个 201，19 个 409，0 个 5xx，日历上恰好 2 格被占。

**实际**（第一次，座位 A-01，2026-11-22）：

```
耗时 170 ms
状态码分布：{201: 1, 409: 19}
成功 1 个
  reservation id=1 status=PENDING
失败原因：{409: '该座位在所选时段已被预约'}
日历上座位 A-01 的占用格：[0, 1]
```

**实际**（恢复索引后复验，座位 A-03，2026-11-23）：

```
耗时 129 ms
状态码分布：{201: 1, 409: 19}
成功 1 个
  reservation id=60 status=PENDING
失败原因：{409: '该座位在所选时段已被预约'}
日历上座位 A-03 的占用格：[0, 1]
```

## 5. 实验 B：移除唯一索引

**操作**：

```sql
-- 外键 fk_reservation_slots_seat_id_seats 依赖 seat_id 上的索引，
-- 所以必须先补一个单列索引，再删唯一索引
ALTER TABLE reservation_slots ADD INDEX ix_tmp_seat_id (seat_id);
ALTER TABLE reservation_slots DROP INDEX uq_reservation_slots_seat_slot;
```

然后同样的 20 并发请求（座位 A-02，2026-11-23）。

**预期**：20 个请求全部 201，同一格子出现多行重复记录。

**实际**：

```
耗时 177 ms
状态码分布：{201: 20}
成功 20 个
  reservation id=40 ... id=59（共 20 条，全部 PENDING）
失败原因：{}
日历上座位 A-02 的占用格：[0,0,...,0,1,1,...,1]（40 个元素）
```

数据库计数：

```sql
SELECT COUNT(*) FROM reservation_slots WHERE seat_id=2;                  -- 40
SELECT COUNT(*) FROM reservations WHERE seat_id=2;                       -- 20
SELECT COUNT(DISTINCT slot_index) FROM reservation_slots WHERE seat_id=2; -- 2
```

即：该座位当天只有 2 个格子，却写入了 40 行占用记录，**每个格子被 20 个人同时占住**。

## 6. 对照表

| 指标 | 实验 A（有唯一索引） | 实验 B（无唯一索引） |
| --- | --- | --- |
| 成功预约数 | 1 | 20 |
| 冲突返回数（409） | 19 | 0 |
| 服务端错误（5xx） | 0 | 0 |
| 落库明细行数 | 2 | 40 |
| 去重后实际时段数 | 2 | 2 |
| 单格重复占用 | 无 | 每格 20 条 |
| 耗时 | 170 ms / 129 ms | 177 ms |

## 7. 结论

1. **正确性由数据库保证**：移除唯一索引后，20 个合法请求全部成功，应用层的业务校验（封禁、日期窗口、每天上限、用户自身重叠）一次都没拦住——因为它们检查的都是"这个用户"和"这个时间窗口"，而不是"这个格子是否已存在"。
2. **"先查再插"在并发下不可靠**：两个事务都先 `count()` 得到 0、再 `INSERT`，都能通过检查；只有唯一约束在提交那一刻拦得住。
3. **异常必须翻译成业务语义**：唯一约束冲突在 ORM 层表现为 `IntegrityError`，服务层 `rollback()` 后返回 409 与明确文案，客户端才能区分"你重复提交"和"座位被别人抢了"，而不是一个 500。
4. **回滚不可省略**：捕获 `IntegrityError` 后不 `rollback()`，会话会进入失效状态，后续请求报 `PendingRollbackError`。

## 8. 局限与后续

- 本机单机压测，未覆盖网络延迟、连接池打满、长时间稳定性。
- 并发数 20，只能证明"竞态窗口存在且被约束挡住"，不能代替容量测试；后续可用 Locust/k6 做阶梯压力测试。
- 未测试"应用层加 Redis 分布式锁"的版本；下一步可对比"仅唯一索引"与"唯一索引 + 锁"在 QPS 与平均延迟上的差异。
- 数据库侧未开启慢查询日志与 `performance_schema` 观测。

## 9. 面试问答预案

**Q：你怎么保证不超卖？**
A：把预约展开成"座位 × 日期 × 时段"的明细行，在 `(seat_id, date, slot_index)` 上建唯一索引；并发写入时数据库只允许一个成功，其余抛 `IntegrityError`，服务层转为 409。

**Q：为什么不在代码里先查一下有没有被占？**
A：查和插之间有窗口，两个请求都能查到 0 条；只有唯一约束在提交时能拦住。业务预检查可以留，但只用于给出更友好的文案，不能当作正确性保证。

**Q：压测怎么做的？**
A：20 个真实注册用户并发 POST 同一座位同一时段。有索引时 1 成功 19 冲突；临时移除唯一索引后 20 个全部成功，库里同一格子出现 20 条重复记录，反向证明了约束是唯一防线。

**Q：如果将来要加缓存或分布式锁呢？**
A：那只是减少无效写入的手段，正确性仍在唯一索引；锁失效或缓存穿透时，数据库仍然兜底。
